# Perl / CPAN 保守リスク診断 — 試験サービス仕様 v0.2

**更新:** 2026-11-15  
**位置づけ:** 初回顧客への提案に使う公開仕様ドラフト。提供実績や価格の妥当性は未検証。個別契約に先立ち対象・納期・守秘条件を確定する。

## 1. 顧客への約束

**古いPerlシステムを、いきなり書き換えずに使い続けるための判断材料を提供する。**

CPAN依存関係・互換性・既存テスト/CIの状況を、提示された資料と許可された範囲の検証から整理する。単なるモジュール一覧ではなく、**根拠、未確認事項、優先順位、次に実施すべき対策**を1つの報告書にまとめる。

診断は「現時点で確認できた保守上の懸念」の整理であり、システムの安全性や無停止運用を保証するものではない。

## 2. 試験価格・対象範囲

**55,000円（税込・1診断）**。相場として確認された価格ではなく、初回販売の検証用の固定価格案。

| 項目 | 1回の診断に含む範囲（試験条件） |
| --- | --- |
| 対象 | 単一のPerlアプリケーション/リポジトリ **1件**、または同等の単一モジュール群 |
| 実行環境 | Perlのバージョン **1種類**、OS/コンテナ等の環境 **1系統** |
| 依存関係 | 直接依存のCPANディストリビューション **最大20件を目安** に一覧化。間接依存は入手できたロック情報等の範囲で記載 |
| 詳細調査 | リスクが高いと考えられる依存・テスト・CIの論点を **最大5項目** 深掘り |
| 調査方法 | 提供資料・コードの静的確認が中心。実行テストは、環境が安全に再現でき、事前合意がある場合に限る |
| 作業時間 | **合計6時間以内**（事前確認から納品・説明まで）を標準上限として設計 |
| 納品形式 | MarkdownまたはPDFの報告書1式、必要に応じて一覧表を付属 |
| 説明 | 納品時の確認・質疑を1回、**30分以内** |

「20件」「5項目」「6時間」は初期の事業検証のための**設計上の仮置き**。実際の案件では資料の状態と難易度を見て事前合意する。対象内でも安全に調査できない場合は、未検証として明記する。

### 受注できる条件

1. 調査の対象と期待成果が明確で、読み取りを許されたソースや資料を確認できる。
2. 対象環境・Perlバージョン・既存テスト状況について最低限の情報がある。
3. 診断に必要なアクセス権が明示され、秘密情報を安全な方法で受け渡せる。
4. 本番変更・緊急復旧を期待していない。
5. 6時間の上限で価値ある成果を出せると事前に判断できる。

情報が不足する案件は、無理に固定価格で引き受けず、対象を縮小するか別途見積もりを行う。

## 3. 作業内容と標準工数（見積もりモデル）

| 作業 | 時間の目安 | 主なアウトプット |

| 事前ヒアリングと対象確定 | 0.5時間 | 対象・前提・除外範囲 |
| 依存関係の抽出・整理 | 1.5時間 | 直接依存一覧、把握できた間接依存 |
| 保守・互換性リスクの根拠確認 | 1.5時間 | リスク最大5項目と優先度 |
| テスト・CIの現状確認 | 1.0時間 | 実行可否と改善提案 |

| 納品説明・質疑 | 0.5時間 | 説明・未解決事項の整理 |

**採算評価:** 初回納品後に実作業時間を非公開で記録し、55,000円の試験価格で再現可能かを検証する。ここに示す工数は達成済みの実績ではない。移動、見積作成、営業、税務・決済等の間接コストを含めた利益は未検証。

## 4. 調査すること

- **依存関係:** `cpanfile`、`cpanfile.snapshot`、`META.json`/`META.yml`、`Makefile.PL`、`Build.PL` など、入手できる定義を確認する。定義不足や実際の読み込みとの不一致があれば記載する。
- **環境の再現性:** Perlバージョン、OS、依存バージョン固定の有無、インストール手順が確認できるかを整理する。
- **保守状況・互換性:** 更新状況、既知の非互換、対象のPerl/OSでのテスト情報など、根拠を確認できた範囲に限り評価する。未確認は推測で埋めない。
- **テスト・CI:** 既存テストの有無、実行手順、CI定義、再現手段の欠落を調べ、改善の最初の一手を提案する。
- **優先順位:** 影響と確からしさ、対処工数を区別して整理する。

実際にコードを実行する場合は、**顧客が許可した隔離環境のみ**を使用し、コマンドと対象を合意する。顧客の本番環境で検証しない。

## 5. 納品物

[診断レポートの目次・記載例](sample-diagnostic-report.md) を標準ひな形とする。

1. **診断サマリー** — 対象、調査条件、主要懸念、推奨順序。
2. **依存関係一覧** — モジュール/ディストリビューション、把握できたバージョン、利用根拠、未確認事項。
3. **リスク台帳** — 事実、根拠、影響、優先度、確認できなかったこと。
4. **テスト・CI所見** — 現状、再現性、改善案。
5. **保守ロードマップ** — まず実施すること、次段階の調査・改修案。
6. **制約・調査していない範囲** — 安全性の保証ではないことを明示。

「依存している可能性」と「確実に依存している」は区別し、確認手段と根拠を残す。実行していないテストは「未実行」と明記する。

## 6. 含まれない作業

- 侵入テスト、網羅的な脆弱性検査、セキュリティ監査・認証、脆弱性ゼロの保証。
- 本番環境へのログイン・変更、デプロイ、緊急復旧、24時間/休日対応。
- コードの修正やテスト追加、CPANモジュールの更新、CIの修復、移行作業の実施。
- 複数システム/複数環境の比較、20件を大きく超える直接依存の網羅的調査。
- 第三者の非公開情報へのアクセスや、許可されていない外部サービスへのコード送信。
- 仕様書にない問い合わせ対応や、無期限のサポート。

### 追加見積もり・中断の条件

対象数の増加、想定外の依存関係、再現環境の新規構築、修正依頼、資料不足、調査工数が6時間を超える見込みなどが判明した場合、**作業を続けて請求するのではなく、まず状況・調査済み範囲・残課題を説明**する。顧客と「対象を絞る / 別見積もりを合意する / 調査を終了する」を選ぶ。追加の作業・費用は**事前の書面合意**なしに発生させない。

## 7. 納期・検収・支払い（個別契約で確定）

- 目安: 対象・資料・アクセス条件が揃った後、**5営業日程度**を試験運用の想定とする。ただし受注時に個別合意し、このページだけで納期保証はしない。
- 着手条件: 見積もり、対象、納期、納品形式、支払い条件、成果物の取り扱いについての書面合意。
- 検収: 合意した診断対象・形式の成果物が揃っているかで判断する。コードの修正や障害の解消自体は検収条件にしない。
- 料金の支払時期、請求書・消費税表記の扱いは取引条件に合わせて個別に明示する。
- 誤記の修正と、追加の調査・再診断とは分けて扱う。

## 8. 守秘・権利・データ管理

- 顧客のソースコード、ログ、担当者情報、認証情報、非公開の診断結果は、**この公開GitHubリポジトリや公開Issueには書かない**。
- 資料は顧客の権限と利用許可を確認した上で、安全な非公開経路で授受する。必要に応じて秘密保持契約を締結する。
- 原則として個人情報や秘密鍵はマスク・除外して受け取る。不要なデータはそもそも提供を依頼しない。
- 保管場所、アクセス権、第三者サービスへの送信可否、保存期間、返却・削除時期を**受注前に合意**する。
- 診断報告書は個別契約に沿って利用できるようにする。原著作物、第三者ライセンス、一般化したノウハウやOSSへの還元の扱いは契約とライセンスに従う。
- 顧客名・導入事例・匿名化した事例の公表も、識別可能性を確認し、**明示的な承諾がある場合のみ**行う。

## 9. 顧客課題を確かめる質問

1. Perlシステムはどの業務を支えており、止まると何が困るか。
2. 最後にバージョン更新・障害対応・担当者引き継ぎをしたのはいつか。
3. 最も不安な依存・テスト・CIはどこか。
4. 調査を社内/外部へ依頼した経験と、その際の費用・成果は何か。
5. 誰が診断結果を使い、誰が購入を決めるか。
